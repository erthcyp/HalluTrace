HalluTrace · Taxonomy proposal · draft for Wednesday

Two axes, decided from two separate sources of evidence

The field divides hallucination at least seven different ways. Six of them answer the same question — what kind of error is this? Only one asks where did it come from? This proposal takes the strongest option from each side and crosses them, under one hard rule: each axis must be decidable from evidence the other axis never touches.

01What the taxonomy has to satisfy

Before arguing about how to divide, we should agree on what "good" means for this project. Four constraints, which are then used in section 04 to eliminate options — so that options get cut by criteria the team agreed to, not by the preferences of whoever wrote the proposal.

C1 · Automatable

Decidable without a human

We have four months, four people, and roughly 25,000 generations to label. Any category that requires someone to read and judge is unusable at that volume.

C2 · Actionable

Different categories, different fixes

If two categories lead to the same remedy, separating them buys nothing. It is naming, not taxonomy.

C3 · Comparable

Anchored to prior work

Invent every category from scratch and we cannot write related work, and nobody can build on the result.

C4 · Independent

The two axes cannot share evidence

Axis 1 is decided from the model output. Axis 2 is decided from the corpus. If they mix, the cross-tabulation becomes circular.

C4 is the one people overlook

The headline result of this project is a cross-tabulation of the two axes. If axis 1 quietly uses corpus evidence to decide a label, that table is meaningless — it would be crossing one dataset against itself. Every time we add or revise a definition on either axis, we come back and re-check this constraint.

02How the field currently divides it

I grouped every taxonomy across the 29 surveyed papers by its organizing principle — the question it is really sorting on — rather than by category names. Seven principles emerge.

Organizing principleSorts onUsed by
1 · Grounding source Inconsistent with what — the world, or the supplied context Hallucinations Leaderboard · HalluDial · HalluScan · HalluScore · HalluLens · Lynx
2 · Verification locus Where the citation chain breaks HalluHard — reference vs content grounding
3 · Surface form What the error looks like linguistically C-FAITH (6) · HaluEval 2.0 (6)
4 · Severity Obvious error or subtle one RAGTruth · FaithBench · MedHallu
5 · Reasoning complexity How hard the question was FactCHD · HalluWorld
6 · Knowledge scope Breadth of knowledge or depth of it KGHaluBench
7 · Provenance Where it came from in the training data HALoGEN only — Type A / B / C

Principles 1 through 6 all answer the same question: what kind of error is this. Exactly one asks why the error happened — and exactly one paper out of twenty-nine uses it.

03The proposal — two axes

Axis 1 · Failure mode decided from output

LabelOperational definitionVerifier
EXISTENCEThe cited object is absent from the reference indexPyPI · Semantic Scholar lookup
ATTRIBUTIONThe cited object exists but does not support the claim made about itretrieval + entailment
NON_ABSTENTIONThe model answers a question that has no correct answergazetteer + refusal classifier

Inherited from HalluHard's reference-versus-content split, extended with non-abstention from HalluLens and AbstentionBench. All three resolve through an index lookup or a classifier, with no human adjudication — so the axis satisfies C1.

Axis 2 · Provenance decided from corpus

LabelConditionReading
TYPE_Acorrect > 0 · halluc = 0The fact was available; recall failed
TYPE_Bcorrect = 0 · halluc > 0The error is genuinely present in the corpus
TYPE_Cboth = 0Nothing present; the model assembled it
TYPE_ABboth > 0Both present — reported jointly, never forced to one
TYPE_NAno unique ground truthUnmeasurable ≠ absent from corpus

Borrowed wholesale from HALoGEN rather than invented. Reusing their taxonomy makes our numbers comparable to theirs (C3) and sharpens what we actually claim: we are not proposing a new taxonomy, we are the first to operationalize this one automatically across a whole benchmark.

04Why not the other five

Prepared in advance, because these will be asked. Each is eliminated by a named constraint.

PrincipleFailsReason
Surface form C1 + C2 Deciding whether something is an attribute error or a relation error requires a human reader — and once decided, it still doesn't tell you how to fix it
Severity C1 "Subtle" is defined by annotator intuition and cannot be written as a rule code can follow. It is also only meaningful when there is supplied context to compare against, which our tasks do not have
Reasoning complexity wrong unit This is a property of the question, not of the error. It belongs in metadata, not on an axis
Knowledge scope redundant Requires a knowledge graph, and is ultimately a proxy for entity popularity — which we measure directly and more precisely as corpus frequency
Grounding source degenerate Faithfulness requires supplied context, and all three of our tasks are closed-book. The split would collapse into a single cell

05The complete label space

The part that gets forgotten

A taxonomy is not only the kinds of hallucination — it needs labels for outcomes that are not hallucinations too. Without them the denominator of the metric is undefined, and any number we report can be argued with immediately.

SUPPORTED Evidence backs the claim — not a hallucination
ABSTAINED The model declined to answer — not a hallucination; reported separately as abstention rate
UNVERIFIABLE The verifier could not reach a decision (403 · paywall · timeout) — excluded from the denominator
PARSE_FAILURE Atomic claims could not be extracted — excluded from the denominator, but the rate must be reported
HALLUCINATED Labeled on both axes ↓
Axis 1 EXISTENCE · ATTRIBUTION · NON_ABSTENTION
Axis 2 TYPE_A · TYPE_B · TYPE_C · TYPE_AB · TYPE_NA
H = hallucinated claims ÷ verifiable claims
Abstention rate = abstained claims ÷ all claims
Parse-failure rate = parse failures ÷ all responses

H follows HalluHard; abstention is broken out separately following HALoGEN, which calls it response ratio. Why the separation matters: fold abstentions into the denominator and a model that refuses every question scores best, which is absurd. And parse failure must be reported rather than quietly dropped — small models fail to parse often, and hiding that rate would make our numbers look cherry-picked.

06Edge cases and proposed rulings

This is where taxonomy meetings usually spend all their time. Rulings are drafted in advance so the discussion can be about disagreements rather than discovery.

SituationProposed ruling
One response contains several claims, some wrong and some right The unit of labeling is the atomic claim, not the response — except for the code task, which is scored per response, following HalluHard
Cites a real paper, but not the one it meant, with a similar title If any metadata field mismatches it is EXISTENCE, not ATTRIBUTION — strict matching, following HalluHard
Hedged answer: "I'm not certain, but probably X" If a checkable claim is present, check it. ABSTAINED means refusing to answer, nothing weaker
Real package, non-existent function inside it EXISTENCE at the function level — granularity must be settled, see decision 1
More than one answer would be correct TYPE_NA, not TYPE_C. "We cannot measure this" and "this is absent from the corpus" are different findings; conflating them inflates Type C
Different query forms return different counts Needs a combination rule — see decision 2

The schema must store the raw infini-gram count, not a thresholded label. Layer three cannot be reconstructed from binary labels. Getting this wrong now means re-running Phase 4 in week fourteen.

08Three decisions for Wednesday

1

At what granularity does EXISTENCE apply?

The package is real but the function is not — is that one claim or two?

ProposedThree levels, following HALoGEN — install, import, function call — reported separately
AlternativeCollapse to one level. Simpler, but loses the detail HALoGEN found most informative: function-call errors are by far the most common
2

How do we combine counts across query forms?

One fact can be queried several ways and return different counts. Which value decides the label?

ProposedTake the maximum for the labeling decision, store every value in the schema — consistent with treating Type C as an upper bound
AlternativeSum or median. Both inflate Type C and are harder to interpret
3

How many query forms per fact?

More forms means fewer false Type C labels, but more API quota and more time.

ProposedStart at three — literal, function-words stripped, entity order swapped — then measure in Phase 0 how much going to five reduces Type C
AlternativeFix at one. Fastest, but Type C inflates until the numbers stop being credible
